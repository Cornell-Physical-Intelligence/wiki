# CUPI wiki audit — September 8, 2026

Four significant pre-existing issues remain unresolved. This was a source audit with synthetic local reproductions, performed in parallel with the intake improvements. No production requests, real applicant records, or credentials were accessed. This is not a complete penetration test or an assessment of production configuration.

## 1. P1 — An active member can retrieve server-side secrets

At [lib/ops.js:264](../lib/ops.js#L264), operation lookup accepts inherited properties of `OPS`. A mutation with `op: "constructor"` invokes `Object(state)` and returns the entire state as `error`. [api/index.js:332](../api/index.js#L332) serializes that value without the filtering applied by `shapeState`.

Impact: an ordinary signed-in member can read stored Resend API credentials, OAuth refresh tokens, and other users' private preferences. Environment-only secrets are not part of this finding. Confirmed using synthetic state.

Remediation: require an own-property operation allowlist, and ensure mutation error responses can contain only an expected error string. Prioritize this fix; after deployment, assess whether stored credentials need rotation.

## 2. P1 — Uploaded attachments can run scripts on the wiki origin

[api/index.js:404](../api/index.js#L404) accepts the supplied MIME type. [api/index.js:416](../api/index.js#L416) serves it unchanged, with an inline disposition and no response sandbox. An active member can upload HTML or SVG, then share its attachment URL with an administrator.

Impact: opening that document can run script on the authenticated wiki origin, read the interest list, and issue administrator mutations. Confirmed that synthetic HTML receives `text/html` with inline disposition using a mocked handler/storage test; no real administrator session was used.

Remediation: force active content to download, or serve it from an isolated origin with a restrictive sandbox. Apply the serving policy to existing uploads as well as new ones, and prevent MIME sniffing.

## 3. P1 — Archiving can discard incoming submissions

[lib/interest.js:445](../lib/interest.js#L445) reads the live list, then [lib/interest.js:451](../lib/interest.js#L451) saves an archive and clears the entire live list in separate operations.

Impact: a submission arriving after the read but before the clear is deleted without being included in the archive. A concurrent update can similarly be replaced by the stale snapshot. Reproduced by injecting a synthetic row between the archive write and clear; the endpoint returned success while the injected row was absent from both lists.

Remediation: atomically move the exact deleted rows into the archive in a database transaction, or a single data-modifying SQL statement. Test concurrent submissions and simultaneous archive requests.

## 4. P1 — Public callers can replace another applicant's submission

[lib/interest.js:376](../lib/interest.js#L376) treats `confirmUpdate` as sufficient to permit replacement. The write at [lib/interest.js:401](../lib/interest.js#L401) does not require proof that the caller owns the supplied email address.

Impact: someone knowing an applicant's email can replace their name, subteam, project, year, and attachment. The confirmation dialog is a user-interface safeguard, not authentication. This behavior predates the new year field.

Remediation: verify email ownership using a short-lived update link/token, or restrict replacements to administrators. CORS and request throttling do not establish email ownership.
